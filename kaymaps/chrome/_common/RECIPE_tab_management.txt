RECIPE: chrome_tab_management(Google Chrome, macOS, cross-site/site-agnostic)
REG: a_2894(2026-08-29)
GATE: WHY this recipe exists — a_2893 had a real wrong-tab-click incident(clicked a stale/wrong-content tab while trying to switch back to a search-results tab, wasted several steps recovering). Root cause: acted on assumed tab position instead of verifying the target tab's actual title/URL via a11y first. This recipe documents the VERIFY-BEFORE-ACT pattern as the headline fix, plus all tested tab-mechanics.

★★★HEADLINE LESSON(the actual fix for a_2893's incident): before clicking ANY tab(whether by position-guess or by re-finding a "previous" tab), ALWAYS query `AXWindow` title first(`see --a11y --pid $PID --compact | grep AXWindow` — shows the CURRENT ACTIVE tab's page-title+incognito-marker) to confirm you know what's currently frontmost, then locate the TARGET tab via its `AXRadioButton` label(URL/title text) in the `AXTabGroup`, NOT by remembered/assumed screen position(tab positions shift as tabs open/close, remembered coords go stale).

REAL-TESTED MECHANICS(all confirmed via kongtrol+a11y, not assumed from general Chrome knowledge):

1. **Open new tab**: `input chord cmd t --yes` — ✅WORKS. New tab appears as `AXRadioButton "새 탭"` in the tab-strip, confirmed via a11y before/after.

2. **Open new window**:
   - regular new window: NOT tested this round(not needed for site-automation tasks so far).
   - incognito window: menu-path ONLY — Chrome menu "파일"(File) → "새 시크릿 창"(New Incognito Window). `cmd+shift+n` chord NOT supported(kongtrol allows only 1 modifier per chord — confirmed BOTH by direct chord-attempt failure AND by kongtrol's own error message listing supported non-modifier keys). Already documented in `kaymaps/chrome/aliexpress/RECIPE_product_search.txt`, cross-referenced here as the general pattern.

3. **Close tab**: `input chord cmd w --yes` — ✅WORKS. Close-button(`AXButton "닫기"`) count in a11y dump decreased by exactly 1 after cmd+w, confirmed real removal not just visual. ★RISK(CONFIRMED, a_2897/2902/2906): cmd+w on the LAST remaining tab DOES close the whole window — a11y then shows 0 AXWindow(only menu-bar remains), but the CHROME PROCESS ITSELF SURVIVES(confirmed via `pgrep -x "Google Chrome"` still returning a PID) — window-count=0 ≠ process-gone, these are DIFFERENT states, don't conflate them.

3b. **Fully quit Chrome(process termination, not just window-close)**: `input chord cmd q --yes` — ✅WORKS(a_2906, real-tested w/ process-level verification). AFTER closing all tabs(process alive, 0 windows, per §3's risk-note above), cmd+q genuinely TERMINATES the process — confirmed via `pgrep -x "Google Chrome"` returning EMPTY(exit code 1, no match) post-quit, not just window-count=0. No "save changes"/confirmation dialog appeared this run(Chrome typically only prompts if downloads are actively in-progress) — if such a dialog DOES appear in a future run, read it before dismissing(don't blindly force-close if it's warning about something real, e.g. an active download). ★VERIFICATION DISCIPLINE: always use PROCESS-check(`pgrep`/`ps aux | grep`) not window/a11y-check to confirm a genuine full-quit — a11y queries return nothing useful once the process is gone anyway(that absence itself is a weaker signal than an explicit pgrep-empty-result).

4. **Switch tabs — by keyboard(numeric jump)**: `input chord cmd 3 --yes`(cmd+N jumps to tab N) — ✅WORKS. Verified via `AXWindow` title change matching the expected 3rd tab's content.

5. **Switch tabs — by keyboard(cycle)**: `input chord ctrl tab --yes`(cycle forward) — ✅WORKS, confirmed via AXWindow title advancing to the next tab in sequence. `ctrl+shift+tab`(cycle backward) — ❌BLOCKED, kongtrol rejects `shift` as a bare chord-key argument in this position(same 1-modifier-limit root cause as cmd+shift+n) — no backward-cycle chord available, use cmd+N(direct jump) or click-by-title instead.

5b. **Switch BETWEEN Chrome WINDOWS(not tabs)**: `input chord cmd '`' --yes`(cmd+backtick, literal backtick character as the key arg — the key-NAME "grave" is NOT supported, must pass the literal `` ` `` character) — ✅WORKS(a_2895, real incident-driven discovery). Cycles to the next Chrome window(e.g. from an incognito window to a regular window, or vice-versa) — REQUIRED when multiple Chrome windows are open(common in this project: 1 incognito for guest-mode-required sites + 1 regular for others) and a tab-strip a11y-query needs to target a SPECIFIC window, not whichever one last had focus. ★real incident: a_2895's first tab-click(coord from a stale query) landed in the WRONG window because 2 windows were open — cmd+backtick fixed it by explicitly cycling to the correct window BEFORE re-querying the tab-strip.

6. **Switch tabs — by click(★the reliable method, use this over keyboard-jump when tab ORDER/POSITION isn't certain)**: query `AXTabGroup`'s child `AXRadioButton` elements — each tab's FULL URL or page-title is the button's label text(e.g. `AXRadioButton "ko.aliexpress.com/w/wholesale-Logitech-MX-Master.html?..." @(242,60)`). Match by title/URL SUBSTRING before clicking(don't click by remembered coordinate — a11y-verified label-match is the ground truth, tab positions shift).

7. **Identify active/frontmost tab**: `see --a11y --pid $PID --compact | grep AXWindow` — the FIRST(topmost) `AXWindow` result's title = the CURRENTLY ACTIVE tab's page-title, plus reveals "(시크릿 모드)" suffix if it's an incognito window(useful for guest-mode-verification tasks per aliexpress recipe's GATE). ★USE THIS BEFORE EVERY TAB-SWITCH DECISION, not just after.

8. **Navigate within a tab(address bar)**: `input chord cmd l --yes` focuses the address bar(confirmed via typing immediately after and screenshot-verifying text landed in the address-bar autocomplete dropdown, not elsewhere on the page) → `input text "<url>" --yes` → `input key return --yes`(or `input key esc --yes` to cancel without navigating, also confirmed working).

VERIFY(general, applies to all above):
- After ANY tab-open/close/switch action, re-query `AXWindow`(active-tab-title) AND/OR `AXTabGroup`(full tab-strip) — don't assume success from the command alone(kongtrol doesn't throw errors on logical failures like wrong-tab-focus, only reports the physical input was sent).
- Tab positions in the strip SHIFT as tabs open/close — never hardcode a tab's screen-coordinate across multiple actions, always re-query.

LIMIT/OPEN:
- Regular(non-incognito) new-window flow not tested(no current use-case needed it).
- Tab-drag-to-reorder, tab-pinning, tab-groups(Chrome's native grouping feature) not tested — out of scope for current automation needs.
- `cmd+shift+tab`(alternate backward-cycle binding some Chrome versions support) not tested — likely blocked by the same shift-chord limitation as ctrl+shift+tab, not confirmed.
