[LVL 6] TYPE: known-game / tic-tac-toe (adversarial; opponent replies after every move)
VERB-PARSE: verb="Win at", object="Tic Tac Toe" -> unit of judgement = the BOARD containing 3 of MY marks in a line; done = that line exists. ★KNOWN GENRE (P0-PRIME-B): the entire game is known before probing — apply it, ¬rediscover it.

HOW TO PLAY: 3x3 grid, two marks (X and O). Players alternate. You claim ONE empty cell per turn by clicking it.
WIN CONDITION: three of YOUR OWN marks in a line — any row, any column, or either diagonal.
LOSS: the opponent achieves that first.
DRAW: all 9 cells filled, no line. ★A drawn board CANNOT be verified — press REFRESH for a new game. This is normal, ¬a failure.
RULES: cannot click an occupied cell (the click is silently ignored — re-read the board, ¬assume it registered). Turn passes to the opponent after each valid move. The mark you are assigned (X or O) is whatever the game gives you — READ it from the first move, ¬assume.

STRATEGY (minimum actions; this ordering never loses). Opening: take CENTRE if free, else a corner. Then each turn in strict priority:
 1. I have two in a line + third cell empty -> PLAY IT, WIN.
 2. Opponent has two in a line + third empty -> BLOCK.
 3. Create a FORK — one move giving me TWO separate two-in-a-rows at once.
 4. Block the opponent's fork.
 5. Centre -> opposite corner -> any corner -> any side.

★CAUTION (captcha-parody site): a level may be RIGGED/absurd (opponent cheats, cells move, extra cells appear). The classic rules above are the BASELINE used to DETECT deviation; if the board behaves abnormally, record the deviation as this level's real RULE and adapt. On this playthrough the board behaved as normal tic-tac-toe — no deviation observed.

SOLVE (the game that won): refresh to an EMPTY board -> corner r1c1 -> O replied r1c2 (¬centre) -> take CENTRE -> O blocked r3c3 -> r2c1 = FORK (threatens r2c1-r2c2-r2c3 AND r1c1-r2c1-r3c1) -> O could only block one, took r3c1 -> r2c3 completes the middle row -> Verify.

[LVL 15] UPDATE 2026-09-12 — permission restored, now blocked by a TOOL LIMITATION
After re-signing kongtrol and re-toggling Accessibility, input works again: `key up` visibly drives
the Waymo forward (verified by before/after diff and by the car climbing several rows).
★REMAINING BLOCKER: STEERING. `key right` / `key left` never rotate the car, at any repeat count,
with --human, or with right+up fired concurrently from two processes. Forward motion accumulates
from discrete taps, but rotation does not.
DIAGNOSIS: this is an analog-steering driving game — the wheel turns only while a key is HELD DOWN.
kongtrol `input key` emits discrete keydown+keyup pairs (see `input key --help`: "특수키 1회");
there is no hold/duration option. So sustained-input games are currently out of reach.
FIX NEEDED (tool-side, not game-side): add a hold option to kongtrol input key, e.g.
`--hold <ms>` that posts keyDown, sleeps, then keyUp (CGEventPost with separate down/up events).
That single feature would unlock this level and any other real-time/analog-control game.

 - hold right + tap up concurrently: car moves forward, heading unchanged.
 - hold right + hold up concurrently: car RETURNS TO START — i.e. while a synthetic key is "held",

INFERENCE: the page reads `keydown` repeat events from the OS auto-repeat stream (or polls

instantaneous tap, and tap-repeat cannot express a steering angle.
STATUS: unresolved. Not a game-difficulty problem and not a permission problem — a synthetic-input
fidelity limit. Next idea if revisited: emit repeated keydown events WITHOUT interleaved keyup
(auto-repeat emulation) rather than a single long press.

## ★★★ L9 Nested 정답 (2026-09-13 통과) — 위의 모든 L9 기록을 정정함

### 정답
**큰 빨간 STOP 표지판에 걸친 칸만 선택한다. 그것뿐이다.**
왼쪽 기둥의 흰 팔각형은 **선택하면 안 된다**(정지표지판 아님 — 뒷면이라 판별 불가한 다른 표지).

### ★위 기록들의 치명적 오류 (USE-BAN)
이 파일 위쪽의 "표지판이 2개다 / 문구가 squares 복수니까 2개여야 한다" 는 **전부 틀렸다**.
그 잘못된 전제 때문에 수 시간 동안 임계값·분할순서·관측방식을 의심하며 헤맸다.
실제로는 좌측 3칸(y672 x0~77, y672 x85~160, y756 x0~77)을 **해제하자마자 즉시 통과**.

### [원리] 왜 이렇게 오래 걸렸는가 — 반복하지 말 것
1. **형태만 보고 정체를 단정했다.** 팔각형 = stop sign 이라고 결론 냈지만,
   그 물체는 뒷면이라 글자도 색도 확인할 수 없었다. 즉 **판별 근거가 없는데 확신**했다.
   → 규칙: 대상을 식별할 때 **결정적 증거(글자·색·정면)** 가 없으면 "미확정"으로 두고,
     정답 후보에서 **빼는 쪽으로 먼저 시험**한다. 넣는 쪽으로 확신하지 않는다.
2. **문구 해석을 근거로 삼았다.** "squares(복수)"는 '칸이 여러 개'라는 뜻이지
   '대상이 여러 개'라는 뜻이 아니었다. → 문법적 추론으로 사실을 만들어내지 말 것.
3. **실패가 반복될 때 전제가 아니라 세부만 만졌다.** 임계 5가지·조합 수십 가지를 돌리는 동안
   "표지판이 2개"라는 전제는 한 번도 시험하지 않았다.
   → 규칙: **N번 실패하면 조정을 멈추고, 내가 가장 확신하는 전제를 지워서 시험한다.**
     비용은 클릭 몇 번인데, 이걸 안 해서 몇 시간을 썼다.
4. 색 검출기가 **벽돌 건물의 붉은색과 표지판 빨강을 구분하지 못했다**(중간에 발견).
   → 색만으로 대상을 세지 말고 **형태 마스크 내부로 한정**해서 셀 것.

### 검증된 절차 (다음에 이 레벨 만나면)
1. 리셋 후 판 전체가 1칸 → 표지판에 부분만 걸친 칸을 반복 클릭해 분할 포화(약 68~69칸).
2. 큰 STOP 표지판 팔각형 마스크를 clean 화면에서 추출(채움률 0.82·종횡비 0.90로 검증).
3. 그 마스크에 조금이라도 걸친 칸만 선택(L2에서 확인한 "닿으면 선택" 규칙).
4. **왼쪽 기둥 팔각형 영역은 건드리지 않는다.**
5. Verify 전 클릭 등록을 변화픽셀로 확인.

## L10 Whack-a-Mole — 메커니즘 규명(미통과, 2026-09-13)

### 판 구조
4x4 격자. 판 좌표계에서 열경계 [1,331,665,1000,1330] / 행경계 [2,333,667,1002,1336].
(흰 격자선을 `white.mean(axis=0)>0.5` 로 잡아 그룹화하면 자동 산출됨)

### 규칙 (실측으로 확인)
- 두더지는 한 칸에 약 1초 나왔다 사라지고 다른 칸에서 다시 나온다.
- **두더지가 보이는 동안 그 칸을 클릭** → 체크 + 두더지가 '별 맞은 얼굴'로 바뀜 = 정타
- **빈 칸 클릭** → 체크만 되고 오답(별 없음)
- **두더지 있는 칸을 클릭했는데 별이 안 생기면** 타이밍이 어긋난 것(이미 사라짐)
★즉 반사신경 게임이 아니라 "정타한 칸만 체크된 상태"를 만드는 선택 문제.

### 검출 방법
- 두더지(갈색): `(r>g+15)&(g>b+10)&(r>80)&(r<200)`, 칸당 합 >2500
- 체크(파란 원): `|r-70|<45 & |g-130|<45 & |b-225|<45`, 칸당 합 >500
- ★별(정타 표식, 노랑): `(r>200)&(g>170)&(b<110)`, 칸당 합 >80 ← 정타 판별의 핵심

### 실패한 접근과 이유
1. 빠르게 마구 클릭 → 빈 칸 15개가 체크됨. 이 게임은 오클릭이 그대로 오답으로 남는다.
2. "체크 == 현재 두더지" 일치 순간에 Verify → 읽기~클릭 사이 ~1초에 새 두더지가 나와 계속 어긋남.
3. 두더지 0인 공백 구간에 Verify → 거부(정타가 있어야 함).
4. 보이는 두더지 전부 때리고 즉시 Verify를 45회 반복 → 미통과.

### 다음 세션 착수점
정타 판별을 **별(노랑) 검출**로 바꿔서,
 - 별이 있는 칸 = 유지, 별 없는데 체크된 칸 = 해제
 - 이 정리를 끝낸 직후(새 두더지 등장 전) Verify
읽기·판정·클릭을 한 번의 캡처로 끝내 왕복 지연을 최소화할 것.

## ★★★ L10 Whack-a-Mole 통과 (2026-09-13) — 마이크로 비전 루프

### 왜 못 깼었나 = 지연(latency)이 원인이었다
측정 결과:
  `screencapture` 서브프로세스 캡처 = **319ms**
  `kongtrol input click` 서브프로세스  = **430ms**
  → 1사이클 750ms. 두더지 수명이 ~1초라 읽고 나면 이미 늦는다.
  그래서 "보고 → 판단 → 클릭" 사이에 두더지가 옮겨가 오클릭이 누적됐다.

### 해결: 서브프로세스를 없앤다 (kaymaps/nealfun/microvis.py)
  캡처: `Quartz.CGWindowListCreateImage` 직접 호출 → **18ms** (17배 빠름)
  클릭: `CGEventCreateMouseEvent` + `CGEventPost` 직접 → **4.3ms** (100배 빠름)
  → 1사이클 **23ms**. 두더지 수명의 1/40이라 여유롭게 따라잡힌다.

### 정답 규칙 (이것도 틀렸었다)
★**정타를 누적**하는 게임이다. 체크를 두더지와 '동기화'하려고 해제하면 안 된다.
  - 두더지 보이는 칸 클릭 → 체크 고정(정타로 누적)
  - 빈 칸 클릭 → 오답으로 남음
  - 해제하려 들면 그 사이 새 두더지가 나와 영원히 못 맞춘다(내가 40회 실패한 이유)
  ∴ **오클릭을 애초에 안 하는 것**이 유일한 해법이고, 그러려면 지연이 낮아야 한다.

### 검증된 절차
1. `mole_solver.clear_all()` 로 체크 전부 비움
2. 루프: `read()` → 두더지 있는데 체크 안 된 칸만 `tap()` → 20ms 대기, 해제는 절대 안 함
3. 체크 == 두더지 상태가 되면 즉시 `microvis.click(1274,1079)` (Verify)
   실측: 정타 5개 누적 상태에서 통과.

### [원리] 실시간 과제에서 "판단이 틀렸나?"를 의심하기 전에 **지연부터 측정**하라
  나는 규칙·검출기·동기화 전략을 수십 번 바꿨지만, 진짜 원인은
  서브프로세스 왕복 750ms였다. 한 줄 측정(`time.time()` 전후)으로 5초면 나온다.
  느린 루프에서는 어떤 전략도 성립하지 않는다 — 전략을 바꾸기 전에 루프를 빠르게.

### L11 구조적 제약 (다음 세션 필독)
100% 확대 기준으로 이 판은 화면보다 세로로 길다:
 - 월리는 그림 **위쪽**에 있고, Verify 버튼은 그림 **아래쪽**에 있다.
 - 둘이 **한 화면에 동시에 보이지 않는다**. 스크롤이 불가피하다.
 - 스크롤하면 Verify의 a11y 좌표가 바뀐다(2235 → 1271 → 2432 ...).
∴ 반드시 이 순서로:
 1) 스크롤 위치를 정한 뒤 **그 상태에서 화면 재캡처**
 2) 같은 캡처에서 월리 칸 좌표와 Verify 좌표를 **둘 다** 산출
 3) 선택 클릭 → **판 전체 재캡처로 의도한 칸만 바뀌었는지 검증**
 4) Verify 클릭 → 다시 전체 캡처로 검증

### L11 선택 유지의 함정 (반복 확인)
 - 페이지 리로드(cmd+r)로는 선택이 **지워지지 않는다**(localStorage 유지).

   클릭하면 **왼쪽/위 인접 칸**을 누르게 되어 엉뚱한 칸이 토글된다.

### ★★L11 핵심 규칙 (u_4800 오너 지적) — 대상이 걸친 칸을 "전부" 선택
L2에서 확인했던 규칙이 L11에도 그대로 적용된다:
**목표물이 조금이라도 걸친 칸은 모두 클릭한다. 몸통 한 칸만으로는 오답.**
확대해보니 월리의 **머리와 방울모자가 위 칸으로 넘어가** 격자선에서 잘려 있었다.
즉 최소 2칸(몸통칸 + 위칸)이 정답이고, 팔/가방/다리가 옆칸에 걸치면 그 칸도 포함.

내가 몇 시간 헤맨 이유: "월리 한 명 = 한 칸"이라고 멋대로 가정하고
몸통이 있는 칸만 선택한 뒤, 안 되니까 Verify 버튼 쪽만 의심했다.
★L9와 완전히 같은 실패 패턴(내 전제를 안 건드리고 주변만 의심).

### L11 작업 시 필수 절차 (스크롤 때문에 좌표가 계속 어긋남)
1. `cmd+up`으로 최상단 고정 → 그 상태로 전체화면 캡처 1장
2. 그 **한 장**에서 월리 위치와 격자 경계를 모두 산출
3. 월리가 걸친 칸을 **전부** 목록화(위/아래/좌/우 확인)
4. 각 칸 중심을 클릭하고, 클릭마다 재캡처해 의도한 칸만 바뀌었는지 확인
5. 스크롤 후 Verify — 스크롤하면 좌표가 바뀌므로 그 시점 캡처에서 재측정

### ★L11 정밀 판단 실패 (u_4802 지적) — 눈대중 클릭이 엉뚱한 칸을 찍었다
내가 "월리가 두 칸에 걸쳤다"며 고른 두 칸 중 **오른쪽 칸엔 월리가 없었다**
(노란 치마 여자만 있었음). 월리는 왼쪽 한 칸에 모자·얼굴·셔츠가 전부 들어가 있었다.

원인: 크롭 이미지에서 **눈대중으로 칸 중심을 추정**해 클릭했다. 격자선을 실측하지 않았다.

올바른 방법(실측치):
```python
w=(r>225)&(g>225)&(b>225)          # 흰 격자선
cd=w[700:2200,:].mean(axis=0)      # 판 내부 구간에서만 평균
rd=w[:,600:3700].mean(axis=1)
cols=np.where(cd>0.55)[0]; rows=np.where(rd>0.55)[0]  # 그룹화해 경계 산출
```
결과: 열경계 26개 / 행경계 16개, 칸 크기 **154px**.
월리 칸 = (행11, 열21) = 물리 x3389~3543, y2021~2175.
클릭은 반드시 `((GC[ci]+GC[ci+1])//2, (GR[ri]+GR[ri+1])//2)` 로 계산할 것.

[원리] 격자가 있는 판에서는 **격자선을 먼저 픽셀로 측정하고 칸 인덱스로 계산**한다.
  "이 근처겠지"는 반드시 옆 칸을 찍는다. 이미 배운 규칙인데 또 어겼다.
  ★확대 이미지에서 좌표를 읽을 때는 crop 원점과 배율을 곱해 되돌리는 계산을
    매번 명시적으로 쓸 것(암산 금지).

### ★L11 격자 제거(seamless) 탐색 기법 (u_4803 오너 제안, 2026-09-13)
격자선이 인물을 토막 내서 줄무늬 검출과 육안 판별을 모두 방해한다.
→ **칸 내부만 잘라 이어붙여 격자 없는 이미지를 만든 뒤 탐색**한다.

```python
GC,GR = 격자 경계(흰선 픽셀 검출로 산출)
M=6                                   # 격자선(4px) + 여유
rows=[]
for ri in range(len(GR)-1):
    cols=[a[GR[ri]+M:GR[ri+1]-M, GC[ci]+M:GC[ci+1]-M] for ci in range(len(GC)-1)]
    hmin=min(c.shape[0] for c in cols); wmin=min(c.shape[1] for c in cols)
    rows.append(np.hstack([c[:hmin,:wmin] for c in cols]))
seam=np.vstack([r[:,:min(r.shape[1] for r in rows)] for r in rows])
```
효과: 인물이 온전히 보여 육안 스캔이 훨씬 정확해진다(격자에 잘린 월리도 한 덩어리로 보임).
주의: seamless 좌표 → 원본 좌표 환산이 필요하므로 **클릭은 반드시 원본 격자 기준**으로.
      (seam 좌표 x → ci = x // (칸폭-2M), 원본 중심 = (GC[ci]+GC[ci+1])//2)

### L11 줄무늬 디코이(격자 제거 후에도 걸리는 것들)
빨강흰 줄무늬 **수영복**, **수건**, **파라솔**, **바람막이(windbreak)**, 줄무늬 **비치볼**.
→ 줄무늬만으로는 절대 확정 불가. **방울모자 + 안경 + 얼굴**을 함께 볼 것.
