==== ROOT CAUSE of "every episode ends GO_NOT_ENGAGED" ====
R2 (the real one) — TDZ crash killed the whole game loop:
  driveAuto() used `otOff` at game.js:1703 but `const otOff` was declared 42 lines
  LOWER (1745). Temporal-dead-zone => every frame threw
      "Cannot access 'otOff' before initialization"
  loop() propagated it, so the trailing requestAnimationFrame(loop) never ran =>
  the page froze permanently on the first frame after engaging.
  MEASURED: performance.now() stuck at 6197ms, daCnt=0, raf stopped, v=0,
            autoOn=1 but prog=0 forever.
  This is why autoOn looked like it "never flipped": it DID flip, then the game died.
  FIX: hoist `const gp` + `const otOff` above the steering block that uses them.
  GUARD: loop() now wrapped in _loopSafe() — a throw still re-arms rAF, so one bad
         frame can never freeze the game again. window.__loopErrN / __jsErr expose it.

R1 (secondary, why clicking never worked) — mouseup never delivered to #qrun:
  MEASURED evLog on a real CGEvent click at the a11y coord (224,257):
      pointerdown:224,131>qrun/qrun T
      mousedown :224,131>qrun/qrun T
      (nothing further — no mouseup, so no synthesized click, so onclick never ran)
  Sibling <button id=qpark> in the SAME panel at the same y gets the full
  down/up/click sequence. Coordinate + hit-test were both fine:
  elementFromPoint at all 4 corners + center of #qrun == qrun.
  Handler itself is healthy: b.click() => runHit=1, runRet='ok', autoOn=1, parked=0.
  => never depend on the native click for automation. ?go=1 and /ctl reset bypass it.

==== wpLen=2439 vs decoder wp_len=234 ====
NOT two route objects. /tel wpLen is the true auto.wp.length (2439 for 강남역→시청역).
The pixel decoder's 234 is a misread of the HUD digits. Trust /tel, not the decoder.

==== SOFT RESET (throughput) ====
Page reload re-parses ~10MB map+search index => ~50s per episode (38% of 130s).
Soft reset reuses the already-built route: teleports car to auto.wp[0], zeroes
v/steer/offroad, clears crashes+dmg+crashHold+crashHoldT+crashLit+bldStuck+blockT,
hides #crash, resets teacher lane, re-arms auto.on=1.
  page  : window.__softReset()   (also POST /ctl {"reset":1} -> _ctl.rst++ -> page runs it)
  MEASURED setup: 50s -> 1.0s.

==== PITFALLS (each cost real time) ====

  and clear with: curl -s -X POST -d '{"on":0}' http://localhost:8901/ctl
  Use &nomodel=1 in the URL so /ctl on=1 cannot re-enable it.

- kongtrol `see --a11y` reports element CENTERS, not top-left corners

==== SOFT RESET RELIABILITY (added after measuring 3 consecutive resets) ====
The 3rd consecutive reset once came back autoOn=0. Two causes, both "one more call fixes it":
  (a) __runBusy 300ms dedupe window (guards click+pointerdown double-fire) ate the call;
  (b) the previous episode had just hit the arrival test (auto.on=0) so startDrive
      landed one frame early.
__softReset() now checks auto.on after startDrive() and retries once. It RETURNS
{ok, why, wp, t} — the harness must read ok and not assume success.

==== HARNESS NOTE ====
After a reset the car can reach the goal and disengage on its own, so
"autoOn==0" late in an episode is a normal end, not a failure to engage.
Distinguish them by checking autoOn WITHIN ~2s of the reset, and treat a later
autoOn==0 as end-of-episode.
