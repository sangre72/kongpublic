# 리서치 과제: 지각-판단-행동 즉각 실행 파운데이션 모델

## 배경

kong-bot(kongtrol) 세션에서 반복 관찰된 문제의식에서 출발:

- VLM(픽셀 기반 화면 분석)은 요청당 5~30초 소요
- kongtrol의 a11y 트리 접근(OS 메모리에서 구조화된 UI 데이터 직접 조회)은 훨씬 빠름
- 사람은 "생각"(판단) 자체는 0.01초급이고, 느린 건 몸(신경·근육 반응)이다 — AI는 몸이 없으니 그 지연이 없는데, 대신 지금은 "생각"(LLM 추론) 자체가 느리다
- 트랜스포머는 방대한 데이터가 있어야 동작하는데, 이는 귀납적 편향(사전지식)이 없어서 모든 규칙을 데이터로 재발견해야 하기 때문
- kong-bot은 이미 `kaymaps/RECIPE_*.txt` 형태로 "메뉴얼을 읽고 이해한 규칙"을 축적해왔음 — 이게 트랜스포머의 약점을 보완하는 실마리

## 목표

방대한 사전학습 없이, **화면을 지각 → 논리적으로 판단(된다/안된다/애매하다) → 즉각 행동**하는 초저지연(0.2초급) 파운데이션 모델을 만든다. 통계적 추론이 아니라 규칙 기반 판단에 가까운 구조.

## 관련 기존 연구 분야

| 분야 | 설명 |
|---|---|
| World Model | 환경 관찰→내부 시뮬레이션→행동 결정 (DeepMind Dreamer, Yann LeCun JEPA) |
| Embodied AI | 카메라/화면으로 보고 물리적 행동을 학습하는 에이전트 (로보틱스 연구) |
| Causal / Neuro-symbolic AI | "된다/안된다/애매하다" 같은 논리규칙을 신경망과 결합 |
| Constraint/Reward Modeling | 명시적 제약("하면 안 된다")을 학습에 반영 (RLHF의 constraint 버전) |
| VLA (Vision-Language-Action) | 화면을 보고 판단해서 행동까지 하는 최신 모델 계열 (RT-2, OpenVLA) |
| Sample Efficiency | 왜 트랜스포머는 방대한 데이터가 필요한가 — 귀납적 편향 부재가 핵심 원인 |

## 리서치 과제 목록

### 과제 1: a11y 트리 vs VLM 픽셀 분석 — 속도/정확도 비교 및 하이브리드 설계
- 표준 UI는 a11y 트리(구조화 데이터)로 즉시 판단, 커스텀 그래픽/캔버스/게임 등은 VLM 필요
- "빠른 1차 판단(a11y) → 애매하면 정밀분석(VLM)" 하이브리드 구조 설계
- kong-bot의 실제 kongtrol 사용 데이터로 벤치마크

**실증 데이터(2026-08-31, 이 맥 M3 Max에서 직접 측정)**:
- a11y 조회(`kongtrol see --a11y --compact`): 평균 30.6ms(5회)
- 스크린샷 촬영(`screencapture -x`, VLM 추론 이전 단계): 평균 168.9ms(5회) — 이미 5.5배 느림
- a11y + 텍스트매칭 파이프라인 전체: 평균 243ms(다국어 텍스트 exact-match 포함)
- 다국어 정확도: Chrome a11y 트리에서 한글 "저장" 텍스트가 정확한 문자열로 그대로 추출됨(`AXStaticText: "모든 변경사항이 저장되었습니다"`) — VLM처럼 이미지에서 "읽어야"(OCR급) 하는 게 아니라 OS가 이미 아는 문자열을 그대로 가져옴. 언어 무관 exact-match 가능, OCR 오류 원천 차단.
- ★이 결과는 새 발견이 아니라, kong-bot이 이미 `kongtrol-base-reference.md`+여러 `kaymaps/RECIPE_*.txt`에 표준으로 박아둔 "a11y 좌표/텍스트가 항상 우선, 픽셀 눈대중·VLM 판독 불신" 원칙을 수치로 실증한 것.

**실증 데이터 2(2026-08-31, CineBot 실제 화면 측정)**: "판단(요소찾기)"과 "물리적 대기(페이지 로딩/네트워크/렌더링)"는 전혀 다른 병목이라 분리 측정 필요.
- 오염된 전체 흐름(새로고침+로딩+분석 혼입): 총 161.5초 — 이 중 새로고침 자체가 31.5초로 최대
- 페이지 이미 로드된 상태에서 순수 a11y 요소찾기만 5회 반복측정: 295~376ms, 평균 326.4ms
- 결론: 목표(0.2초급 즉각판단)에 이미 근접(326ms) — 남은 병목은 "판단"이 아니라 "네트워크/렌더링 대기"이며, 이건 판단모델 개선으로 해결 불가한 별개 영역. 판단모델 연구는 326ms를 더 줄이는 것(kongtrol 프로세스 실행 오버헤드 최적화, 반복화면 규칙캐싱으로 재조회 생략)에 집중해야 함.
- 2차 재측정(5회, 다른 버튼 대상): 182~262ms, 평균≈201ms — 200ms대 초반이 이 환경의 순수 a11y-lookup 기준선으로 재확인됨.
- 3차 재측정(5회, 리로드 없이 완전 정적 상태): 168~253ms, 평균≈188ms — ★목표(0.2초=200ms) 달성 확인.

**실증 데이터 3(규칙캐싱의 한계와 해법)**: 사용자 지적 — 화면배율/폰트크기/줌 설정이 사람마다 달라 좌표(X,Y) 기반 규칙캐싱은 재사용성이 낮음. 해법 = 좌표가 아니라 "라벨/타입"으로 캐싱("(1184,867) 클릭"이 아니라 "'운세 생성' 텍스트를 가진 버튼 클릭"으로 저장) → 실행 시점마다 a11y로 실제 좌표만 재조회(200~330ms), 로직(무엇을 찾을지/할지)만 재사용. 이건 이미 kongtrol-base-reference.md의 "좌표 하드코딩 금지, 라벨 기준 재조회" 원칙과 일치.

**운영상 교훈(2026-08-31, a_2967→2970 체인)**: "새로고침" 버튼이 앱마다 2종류(브라우저 자체 새로고침 vs 앱 내부 새로고침 버튼) 존재할 수 있고, 혼동 시 안 좋은 부작용(페이지 리로드로 미저장 상태 소실) 발생 가능 — 매번 a11y로 정확한 대상(앱 내부 버튼 좌표)을 특정해야 함. 또한 지시서(a_*.txt)는 K7(압축영문+기호) 형식을 지켜야 워커가 분석 없이 즉시 실행 가능 — 산문식 영문 지시서는 그 자체로 지연 요인이 됨(오늘 직접 겪은 실패 사례).

**실증 데이터 4(zoom-crop 병목 분석 + 신규/반복/해상도-변경 3단계 원칙)**: zoom-crop의 촬영 자체(`screencapture -R`)는 85~99ms로 빠름 — 느린 건 잘라낸 이미지를 모델이 "보고 확인"하는 단계로, 이건 VLM 추론과 동일한 병목(zoom-crop도 결국 이미지 인식이라 픽셀→의미 변환 필요). 즉 zoom-crop 자체를 빠르게 만들 수는 없고, **덜 쓰도록 만드는 게 근본 해법**.

3단계 사용 원칙(사용자 정리, 2026-08-31):
1. **신규 앱/화면(처음 다룸)**: zoom-crop 필수(a11y 라벨을 아직 신뢰 못함, 눈으로 직접 검증) → 검증 결과를 레시피에 기록
2. **반복 작업(이미 레시피에 검증됨)**: a11y 라벨/구조 그대로 재사용, zoom-crop 생략 → 200ms대 유지
3. **해상도/배율 변경 시**: 그 새 조건에서만 다시 zoom-crop 재검증 필요 → 결과를 레시피에 "해상도 X 케이스"로 추가

결론: 레시피 = "해상도/조건별 검증 케이스 모음집"으로 계속 확장되는 구조. 한 번 검증된 조건은 영원히 빠르게(200ms급) 재사용, 새 조건을 만날 때만 느린 zoom-crop으로 1회 검증 후 레시피에 편입.

### 과제 2: 레시피(자연어 규칙) → 명시적 규칙표 변환(Rule Extraction)
- `kaymaps/RECIPE_*.txt`를 "IF 화면에 X 있음 AND 상태=Y THEN 행동(X)" 형태로 구조화
- 자연어 레시피 축적 → 기계가 바로 조회 가능한 규칙 데이터베이스로 전환

### 과제 3: 초경량 즉각-판단 모델 학습(Distillation / Behavior Cloning)
- 큰 모델(LLM)이 화면 판단 데이터를 지속 생성
- 그 판단 패턴만 작은 전용 모델(수백만 파라미터급, 트랜스포머가 아니어도 됨 — 결정트리/작은 MLP 포함)에 증류
- 목표 추론속도: 0.2초 이내

### 과제 4: 캐시 우선(Cache-first) 판단 구조
- 이미 본 화면 패턴 → 즉시 규칙 조회(0.01초급)
- 처음 보는 패턴만 큰 모델에 판단 요청 → 결과를 다시 규칙으로 저장(사람의 "배우는" 과정과 동일한 구조)

### 과제 5: Neuro-symbolic 하이브리드 — 규칙(사전지식) + 신경망(애매한 경우 처리)
- 순수 통계학습 대신 명시적 규칙을 사전지식으로 주입해 sample efficiency 개선
- "된다/안된다/중간값(애매함)" 3단 판단 구조를 어떻게 모델링할지

## 프로젝트 비전(사용자 정리, 2026-08-31, u_3206)
> "로봇을 만드는 것과 비슷하다 — 목적을 위해 최단거리로 얼마나 빠른 판단을 할 수 있는지, 그리고 그 판단으로 동작한 액션들이 얼마나 정확한지. 인간적인 것·기계적인 것·하이브리드·인문사회·심리적인 것 다 동원해서 연구. 실적이 베스트일 때까지 반복. 하이쿠로 부족하면 오푸스까지 격상."

핵심 축 2개:
1. **판단 속도**(목표까지 최단시간 의사결정)
2. **행동 정확도**(그 판단에 따른 실제 액션의 정밀도)

접근 다각화: 순수 기계적(구조화 규칙/캐싱) + 인간적(직관/휴리스틱 모사) + 하이브리드(neuro-symbolic) + 인문사회(사용자 맥락/의도 이해) + 심리적(장애·인지패턴 등 다양한 사용자 조건 고려, u_3187에서 언급된 시각/언어장애 패턴 학습 포함).
