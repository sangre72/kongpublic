# 주행 모델 재학습 계획 (u_5108, 2026-09-15)

## 결론 먼저: 기존 32GB 는 **지우지 않는다**

오너 지시는 "쓸 수 없다면 지우고 다시 수집"이었다. 실측해보니 **쓸 수 있다.**

| 검증 | 결과 |
|---|---|
| X.npy 저장 형태 | `(85768, 3, 256, 256) uint8` — **이미 전처리된 256x256** |
| 캡처 버그 영향 | **없음.** 알림바 40px·레티나 2배 문제는 *실시간 캡처* 경로의 버그다. 저장된 학습 프레임은 그때 이미 256x256 로 정규화돼 들어갔다 |
| 모델 적합도 | steer corr **0.991** / thr **0.993** / brake **0.961** (1500 프레임 홀드아웃, GPU) |

즉 데이터도 라벨도 정상이고 모델도 그 데이터를 제대로 학습했다.
**문제는 오염이 아니라 커버리지다.** 지우면 멀쩡한 8.5만 프레임을 버리는 것이다.

## 왜 이렇게 수집됐나 (하네스 원인, 소스 확인)

- `teacher.js:267` `T.lane = 0` 고정. 차로 변경은 `T.setLane()` 호출로만 일어난다.
- `T.setLane()` 을 부르는 유일한 곳은 `build.py:63` 의 `--lanedemo` 블록.
- 수집 빌드에 `--lanedemo` 를 안 걸면 **교사는 평생 한 차로 직진**만 시연한다.
- 교사는 사고가 나면 즉시 도로로 복귀시킨다 → 이탈 상태가 라벨에 거의 안 남는다.
- 경로가 우회전 위주로 뽑혀서 좌회전 시연이 20배 적다.

모델은 시연받지 못한 동작을 할 수 없다. 차선변경·추월·복귀가 안 되는 건
모델 용량 문제가 아니라 **가르친 적이 없는 것**이다.

## 수집 계획 (추가 수집, 기존 데이터에 합침)

목표: 결손 구간만 채워 균형을 맞춘다. 같은 걸 더 모으는 건 무의미하다.

| # | 상황 | 목표 프레임 | 수집 방법 |
|---|---|---:|---|
| C1 | 좌회전 | 8,000 | 좌회전이 많은 경로를 강제 선택. 우회전과 1:1 |
| C2 | 차로변경 (좌/우 각각) | 8,000 | 교사 차로변경 모드. 타이머 아님 — 앞차 상황 기반 |
| C3 | 앞차 추종·추월 | 6,000 | 느린 앞차 스폰 → 간격 유지 → 옆차로 확인 → 추월 → 복귀 |
| C4 | 정지 → 출발 | 4,000 | 적신호 정지, 앞차 정지, 갓길 출발 |
| C5 | 이탈 복구 | 10,000 | ★차를 일부러 비뚤게/차로 밖에 놓고 교사가 되돌아오는 장면 |
| | **합계** | **36,000** | 기존 85,768 + 36,000 = 121,768 |

C5 가 가장 중요하다. 현재 `on_road` 가 전 프레임 1.00 이라 모델은
**차로를 벗어났을 때 어떻게 돌아오는지 배운 적이 없다.** 한 번 벗어나면 복구 불능인 이유다.

## 학습

- 기존 + 신규를 합치되 **클래스 균형 샘플링**(결손 구간 가중치↑)으로 학습한다.
  단순 concat 하면 여전히 기존 8.5만이 지배한다.
- GPU 필수(`gpu_guard.require_gpu()`), MPS. CPU 폴백 금지 — `.claude/rules/gpu-mandatory.md`.
- 검증: 헤드별 홀드아웃 corr + **실주행**(강남역→시청역 진행률·사고수).
  corr 만 높고 주행이 안 되는 건 이미 겪었다. 주행 측정이 최종 기준이다.

## 되돌리지 말 것

- `capture.py` 툴바 자동감지(`height - width`) — 알림바 40px 때문에 brake 0.90 vs 0.29 가 갈렸다.
- `capture.py` screencapture 경로 — CGWindowListCreateImage 가 호출당 30초였다(→172ms).
- `driveModel()` 브레이크 판정: 절대 임계값이 아니라 `brake > thr + 0.1`.
  학습 라벨에서 thr>0.5 와 brk>0.5 동시 발생은 0.00% 다.
