## 1. 갭 분석 — 게임 필요능력 vs 문서 보유 (실측)

docs/adr·docs/research grep 실측 기준.

| 필요 능력 | 리서치(R5 등) | ADR | 상태 |
|-----------|:---:|:---:|------|
| 마우스/키보드 입력 주입 | ✅ R5 §2 | ✅ 0004 input | **보유** |
| 화면 캡처 | ✅ R5 §5 (mss/scrap/xcap) | ❌ | **리서치만 — ADR 미승격** |
| 이미지 매칭/픽셀 조회 | ✅ R5 §5 (OpenCV matchTemplate) | ❌ | **리서치만 — ADR 미승격** |
| OCR (숫자 읽기) | ❌ | ❌ | **부재** |
| 게임 상태 파악(격자/블록 인식) | ❌ | ❌ | **완전 부재** |
| 룰 기반 판단(solver/휴리스틱) | ❌ | ❌ | **완전 부재** |
| 폐루프(캡처→판단→액션) 타이밍 | ❌ | ❌ | **완전 부재 = 최대 빈틈** |

**결론**: R5 §5가 화면 캡처·이미지 매칭을 "GUI 요소 찾기" 용도로 다뤘으나 ADR trait 6종(0002)엔 화면 인식 slot이 없음. [상태 파악→판단→액션] 폐루프는 문서 전체에 없음. → 게임 리트머스를 통과하려면 이 축을 **신규 ADR로 명문화** 필요.

## 2. 화면 인식 (screen sensing) — 실측

### 2-1. 스크린 캡처 크레이트
| 크레이트 | 최신 | 유지 | 플랫폼 | 판정 |
|----------|------|------|--------|------|
| **xcap** | 0.9.8 (2026-08-01) | 활발(월~286k DL) | Win/mac/Linux X11, Wayland 제한 | **1순위** |
| screenshots | 0.8.10 (2024) | xcap로 통합(deprecated) | — | 사용금지→xcap |
| scrap | 0.5.0 (2018) | 방치(RustDesk fork만) | Win/mac/Linux | 비권장 |

> 실시간 고FPS 필요 시 플랫폼별(Windows=windows-capture, macOS=screencapturekit) 분기 가능하나 구현 부담 큼. 크로스플랫폼 단일 = xcap.

### 2-2. 화면→상태 추출 3방법 → **좌표격자+픽셀색 하이브리드가 두 게임 모두 최적**
| 방법 | 정확도 | 속도 | 의존성 | 지뢰찾기 | 테트리스 |
|------|--------|------|--------|:---:|:---:|
| ⓐ 픽셀/템플릿(OpenCV) | 높음 | 빠름 | ★시스템 OpenCV 필수(무거움) | 보조 | 부담 |
| ⓑ OCR(ocrs/leptess) | 정형폰트 높음 | **느림** | ocrs=순수Rust / leptess=시스템 | **과잉** | 부적합 |
| **ⓒ 좌표격자+픽셀색** | 격자고정시 최고 | **매우 빠름(산술)** | 없음(캡처만) | **최적** | **최적** |

- **지뢰찾기**: 격자 좌표 산술 계산 + 셀 중심 픽셀색으로 닫힘/깃발/숫자색(1=파랑·2=초록·3=빨강…) 판별. OCR 불필요.
- **테트리스**: 보드 격자 고정 → 셀 중심 픽셀색으로 채움/블록색·낙하블록 추적. 프레임마다 소수 픽셀 샘플링이 전체 템플릿매칭보다 경제적.
- OCR·OpenCV는 정확도·속도·배포의존성 대비 이득 적어 최후 보조.

### 2-3. ★macOS 캡처 TCC 리스크 (실무 최대 함정)
- xcap의 macOS 백엔드 = legacy CoreGraphics `CGWindowListCreateImage`(소스 실측). 
- 화면 캡처는 TCC "화면 기록" 사용자 승인 필수 — 코드사이닝 entitlement로 부여 불가, 오직 사용자 승인.
- **미승인 시 Err가 아니라 검은/빈 화면 반환**(RustDesk 사례) = 조용한 실패 → kongtrol이 별도 감지·안내 필요.
- Sequoia(15): legacy API 경고·Developer ID 서명 없으면 TCC 등록 불안정. **미확인**: xcap이 미승인 시 Rust Err 반환하는지 → kongtrol 실측 필요.

## 3. 게임 판단 (룰 이해/추론) — 실측

### 3-1. 지뢰찾기 solver (3계층)
- **(a) 기초 제약룰**: 인접지뢰수=깃발수→나머지 안전 / 지뢰수−깃발수=남은미공개수→전부 지뢰. 대부분 판 해결.
- **(b) CSP/집합차감**: 경계셀 제약 부분집합 차감·연결요소 분해·가우스소거로 결정적 안전/지뢰 도출. (하버드: coupled-subsets CSP가 최우수)
- **(c) 확률 추측**: 결정적 수 없을 때만 조합론으로 셀별 지뢰확률 계산→최소확률 셀.
- **커버리지**: Beginner/Intermediate ~100%, Expert ~70% 무추측. **Expert ~30%는 본질적으로 추측 불가피**(실력 아닌 수학적 사실). → 하드코딩 룰봇으로 대부분 커버, 확률 계층은 얇게.

### 3-2. 테트리스 휴리스틱 (학습 불필요)
- 모든 배치(회전×열) 나열→가중 선형함수 평가→최고점 선택. 경량·실시간.
- **4-feature 경량판**(codemyroad, 가장 쉬움): Aggregate Height −0.51 / Complete Lines +0.76 / Holes −0.36 / Bumpiness −0.18. + 다음조각 1-lookahead로 200만+ 줄. → **kongtrol 시작점 권장**.
- Dellacherie/El-Tetris(6-feature)는 최대 ~10만 줄. 실시간 O(배치×셀) 정수연산뿐.

### 3-3. 룰봇 vs ML → **둘 다 룰봇/휴리스틱이 정답, ML 오버킬**
| 게임 | 권장 | 근거 |
|------|------|------|
| 지뢰찾기 | 룰봇(기초+CSP+확률) | 확률은 조합론이 신경망보다 정확 |
| 테트리스 | 휴리스틱(4-feature) | ★RL(DQN/PPO)이 실측상 휴리스틱보다 점수·효율 열세(2025 비교연구) |

> ML은 (1)학습 파이프라인·GPU 부담 (2)비결정·설명불가 (3)테트리스는 성능조차 열세 → CLI 실시간 도구엔 부적합.

### 3-4. 판단 난이도: 지뢰찾기 vs 테트리스
- **지뢰찾기** = 생각 어렵지만 시간 무제한(추론 정확성이 병목).
- **테트리스** = 생각 가볍지만 시간 촉박(실시간 화면인식·입력 파이프라인이 병목).
- → 두 게임이 서로 다른 능력을 시험: 지뢰찾기=추론 로직 축, 테트리스=OS 제어/타이밍 축.

## 4. 폐루프 타이밍 + enigo 게임입력 — 실측

### 4-1. 1사이클 지연 (그리드 게임)
| 단계 | 튜닝 | 나이브 |
|------|------|--------|
| 캡처 | ~10ms (GPU API) | ~30ms (xcap/mss 단발) |
| 인식(픽셀/그리드) | <5ms | ~15ms |
| 판단(휴리스틱) | <10ms (추정) | <10ms |
| 주입(enigo) | ~5ms | ~5ms |
| **1사이클 합** | **~30ms** | **~50–100ms** |

> ★OCR 매프레임 금지(수백ms~초로 폭증). 그리드 컬러 인식이 Tesseract 대비 50–200배 빠름.

### 4-2. 테트리스 실시간 판정
- **핵심**: 봇은 프레임 단위 반응 불필요 — **새 블록 스폰 시 1회 배치 계획** 후 고정 키시퀀스 실행.
- 낙하속도: NES lv0 = 0.8s/cell, 가이드라인 lv1 = 0.8s/cell(~1.25셀/s). 사람 반응 ~200–250ms.
- ✅ **저~중 gravity(≥~0.1s/cell) 감당 가능**: 5FPS(200ms/사이클)로 충분, 사람보다 여유.
- ⚠️ **고 gravity/킬스크린(≥1G, ~16–33ms/cell) 한계**: 캡처+인식 오버헤드가 가용시간 초과 → 화면캡처 봇 무너짐. 기록급 StackRabbit은 에뮬 메모리 직접읽기로 캡처 우회.

### 4-3. 지뢰찾기 타이밍 = 무압박 확인
- 타이머는 점수기록용, 시간 기반 게임오버 없음. 보드 정적. 느려도 이김(캡처봇들이 클릭 딜레이 주입하고도 승리).

### 4-4. enigo 게임입력 현실성
- **(a) 마우스 절대좌표+클릭 ✅**: `move_mouse(x,y,Coordinate::Abs)` + `button(Left/Right, Direction::Click)`. 지뢰찾기 완전 지원.
- **(b) 키 홀드 ✅ / ★자동반복 ⚠**: `key(Key, Press/Release)` 홀드 가능, 하드드롭 `Click` OK. **단 홀드키 OS 자동반복이 Win/mac에서 트리거 안 됨(X11만 정상)** → DAS·방향키 연타는 타이머로 Press 직접 반복 구현(enigo #98).
- **(c) ★합성입력 차단 — 대상 게임 유형별로 갈림**:
  - **브라우저 게임(HTML/canvas): 수용** — OS 합성입력이 `isTrusted=true` 이벤트 생성, JS가 하드웨어와 구별 못함. **최고 신뢰 추천 대상**(단 enigo 명시 성공사례는 미발견, isTrusted 원리 추론).
  - 네이티브 클래식 Win32 지뢰찾기: 동작(레거시 메시지 큐).
  - **네이티브 안티치트/DirectInput/Raw Input(RIDEV_NOLEGACY): 무시·차단** → enigo 불가. 회피 말 것.

## 6. 신규 ADR 필요 항목

> ★기존 ADR 6종에 [화면 인식·판단 폐루프] 축이 없음 → **신규 ADR 필요**.

**ADR 0007 (제안): perception-decision-loop (인식·판단 폐루프)**
- 신규 core trait 2종: `ScreenSensor`(캡처+상태추출: xcap + 좌표격자·픽셀색) + `DecisionEngine`(게임/작업별 룰·휴리스틱 판단).
- 폐루프 아키텍처: `capture → extract_state → decide → act(InputInjector)` 루프. 사이클 예산·rate 제한.
- 위험도/보안: 화면 캡처 = 민감정보 노출 가능(0004 자격증명 마스킹 연계), macOS Screen Recording TCC(별도 권한, 미승인 감지).
- 범위 경계: 게임 봇은 [브라우저 게임·사용자 자기머신·명시 승인]으로 한정(안티치트 우회·네이티브 게임 봇 금지 — 0004 공격도구화 방지 정신).
- 마일스톤 편입: M5(입력주입) 이후 **M7(perception loop)** 또는 별도 트랙. 게임 리트머스는 이 단계 완료 후 검증.

> 판단(DecisionEngine)은 게임별 플러그인(minesweeper solver·tetris heuristic)으로 분리 — core는 인터페이스만.

## 7. 단계적 PoC 제안 (구현 아님 — 제안)

| 단계 | 대상 | 검증 목표 | 근거 |
|------|------|-----------|------|
| **PoC-1** | **브라우저 지뢰찾기** | 폐루프 최초 실증: xcap 캡처→격자 셀 픽셀색 판별→기초룰 solver→enigo 좌/우클릭. 1판 클리어(추측 없는 판) | 정적·턴제=타이밍 무압박, 가장 쉬움 |
| **PoC-2** | 브라우저 지뢰찾기(확률) | Expert 추측 판까지: CSP+확률 계층 추가 | ~30% 추측 불가피 판 대응 |
| **PoC-3** | **브라우저 테트리스(저레벨)** | 실시간 폐루프: 블록 스폰 감지→4-feature 배치→키시퀀스+반복타이머. 저 gravity 지속 | 실시간 파이프라인·타이밍 검증 |

**권장 착수**: PoC-1(지뢰찾기)부터. 성공 시 폐루프 아키텍처(0007) 검증 → 테트리스로 실시간성 확장.
