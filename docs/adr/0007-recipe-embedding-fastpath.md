# 0007. 레시피 임베딩 매칭 패스트패스 (제안, 미구현)

- Status: Proposed (2026-08-25)
- Deciders: user 제안(u_2251), 오케 정리
- Context: kaymaps/ 레시피 축적이 늘어나며(ComfyUI만 해도 오늘 4개 신규) 매번 클로드(워커) 세션을 새로 띄워 처리하는 비용이 커짐.

## Context

현재 구조: 사용자 지시(u_) → 오케가 a_ 지시서 작성 → 워커(클로드 세션)가 처음부터 판단해서 kaymaps/ 레시피를 찾아 참고 → 실행. 이미 확립된 레시피가 있어도 매번 워커가 전체 맥락을 다시 추론해야 하므로 느리고 토큰비용이 크다.

## Proposed Idea (user 2026-08-25, u_2251)

```
사용자 지시
   ↓
[로컬] 임베딩 매칭으로 레시피 시퀀스 후보 즉시 생성 (밀리초 단위)
   ↓
확신도 높음? → 바로 실행 (클로드 호출 없음)
확신도 낮음/새로운 상황? → 클로드에게 전체 계획 한 번에 요청
   ↓
실행 중 에러/예외 발생 시에만 클로드 재호출
```

핵심 아이디어: 사용자 지시를 로컬 임베딩(sentence-transformers 등 경량 모델)으로 벡터화 → kaymaps/ 레시피들의 제목·WHY·태그도 미리 임베딩해 인덱싱 → 코사인유사도로 즉시 매칭. 매칭 확신도가 높으면 그 레시피의 STEPS를 그대로 kongtrol 명령 시퀀스로 변환해 클로드 호출 없이 바로 실행. 확신도가 낮거나 레시피가 없는 새 상황이면 지금처럼 클로드(워커)를 불러 전체 계획을 세우게 하고, 성공하면 그 결과를 새 레시피로 축적. 실행 중간에 에러가 나면 그 시점에만 클로드를 재호출해 복구.

## Rationale (왜 고려할 가치가 있는지)

- 레시피가 이미 "성공 확정"된 반복작업(예: RECIPE_workflow_json_load.txt처럼 좌표·절차가 고정된 것)은 매번 클로드 추론이 낭비 — 결정론적 스크립트 실행으로 충분.
- 반대로 처음 보는 상황(오늘 LTX-2.3 소켓연결처럼 시행착오가 필요한 경우)은 여전히 클로드 판단이 필수 — 이 구분을 임베딩 확신도로 자동화하자는 것.
- 에러시에만 재호출하는 구조는 "확인이 필요할 때만 개입"이라는 기존 원칙([[feedback-dont-ask-researchable-things]] 등)과 방향이 같음 — 사람(클로드)이 매번 관여하지 않고 자동화 가능한 부분은 자동화.

## Open Questions (구현 전 정리 필요)

1. **임베딩 모델·인덱스**: 로컬에서 돌릴 경량 임베딩 모델 선택(예: 이미 로컬 LLM서버가 있음 — [[local-network-llm-server]] 참고 가능), 벡터 인덱스(단순 numpy 코사인유사도로 충분한 규모인지, 아니면 faiss 등 필요한지) 결정 필요.
2. **레시피 → 실행시퀀스 변환기**: 지금 레시피는 사람이 읽는 자연어+좌표 텍스트 — 이를 결정론적으로 실행 가능한 스크립트(좌표는 매번 a11y로 재확인해야 하므로 완전 하드코딩은 위험, RECIPE 자체에 "재확인 절차"가 포함된 것이 많음)로 어떻게 변환할지 설계 필요.
3. **확신도 임계값**: 얼마나 유사해야 "확신도 높음"인지 튜닝 필요 — 너무 낮으면 잘못된 레시피 오적용 위험(예: 비슷해보이지만 다른 앱), 너무 높으면 패스트패스가 거의 안 걸림.
4. **kongtrol과의 결합**: 레시피 실행 자체는 여전히 kongtrol(input click/drag/key)로 이뤄지므로, 이 패스트패스는 "클로드 세션을 안 띄우고 로컬에서 kongtrol 명령 시퀀스를 직접 생성해 실행하는" 별도 실행기(스크립트/서비스)가 필요 — 오케스트레이터 자체 확장 또는 별도 데몬으로 구현 여부 결정 필요.
5. **실패시 폴백 신뢰성**: "에러시에만 재호출"이 안전하려면 실패 판정 로직(어떤 에러가 재호출 대상인지)이 명확해야 함 — [[feedback-realmeasure-before-trust-claim]] 원칙대로 실측 기반 실패판정 필요.

## Extension: 결과판단 3단계 필터 (user 2026-08-25, u_2252)

병목 ③(레시피 실행 후 "성공했는지, 실패했다면 왜"를 판단하는 단계)도 통째로 클로드에 맡기지 말고, **판단과 진단을 분리**해서 단계별로 싸게 처리하자는 확장 제안.

```
레시피 실행
   ↓
[로컬] postcondition 체크 (a11y diff, if문 수준) → 성공이면 끝
   ↓ 실패
[로컬] 에러 유형 분류 (규칙 기반 패턴 매칭) → 알려진 유형이면 재시도/복구 레시피로 처리
   ↓ 못 알아낸 새 패턴
[클라우드] 스크린샷+diff 보내서 진단 요청 → 결과를 규칙에 편입
```

**1단계 — 성공여부 판단(로컬, if문 수준)**: 레시피 작성 시 "이 레시피가 성공하면 a11y 트리에 이런 요소가 나타나야/사라져야 한다"는 **postcondition을 레시피 자체에 명시적으로 정의**해두고, 실행 후 그 조건만 규칙기반으로 체크. 클로드도 로컬 모델도 불필요 — 실행 전/후 a11y 트리 diff 비교만으로 충분.

**2단계 — 실패유형 분류(로컬, 패턴매칭)**: postcondition 불일치 시 "왜" 실패했는지도 흔한 유형은 패턴화 가능:
- 타겟 요소가 a11y 트리에 아예 없음 → "요소를 못 찾음"
- 요소는 있는데 disabled 상태 → "권한/상태 문제"
- 예상 못한 새 창/팝업 등장 → "새 창 등장"
- 클릭됐는데 상태변화 없음 → "타이밍 문제 또는 잘못된 요소"

**3단계 — 진짜 애매한 경우만 클라우드**: 위 규칙으로도 원인이 안 잡히는 새로운 유형(새 앱, 예상 못한 UI 변형)만 스크린샷+a11y diff를 클로드에 보내 진단 요청. 이 경우는 학습가치가 크므로 결과를 로그로 쌓아 규칙에 편입 → 점점 3단계로 가는 빈도가 줄어드는 구조.

### 현황 실측 답변 (u_2252 질문: "지금 레시피에 기대값이 정의돼 있나?")

**부분적으로만 그렇다.** kaymaps/의 RECIPE_*.txt들은 이미 `VERIFY:` 섹션에 기대 상태변화를 자연어로 적어두고 있음(예: RECIPE_workflow_json_load.txt — "탭 제목(AXWindow) 변경 확인이 가장 확실한 로드성공 지표", "실행 버튼 클릭 → '작업이 대기열에 추가됨' 메시지 확인"). 하지만 이건 **사람이 읽는 자연어 지시일 뿐, 워커(클로드)가 매번 그 문장을 다시 해석해서 a11y/스크린샷을 보고 스스로 판단**하는 구조 — 즉 postcondition은 "정의는 돼 있으나 기계 판독 가능한 형태(if문)로 코드화는 안 돼 있음". u_2252 제안대로 하려면 VERIFY 섹션을 자연어에서 구조화된 형태(예: `postcondition: {a11y_element_appears: "AXWindow[title~='<name> - ComfyUI']"}`)로 전환하는 작업이 필요.

### Extended Open Questions

6. **postcondition DSL 설계**: 레시피의 VERIFY 자연어 문장을 기계판독 가능한 조건식으로 표현할 포맷 필요(단순 key-value인지, 작은 표현식 언어인지).
7. **a11y diff 도구**: 실행 전/후 `see --a11y` 결과를 비교하는 diff 유틸리티가 현재 없음 — kongtrol 자체에 추가하거나 오케스트레이터 스크립트로 구현 필요.
8. **에러유형 분류기 정확도**: 4가지 예시 유형(요소없음/disabled/새창/무반응) 외에 실제로 얼마나 많은 실패 패턴이 이 분류에 들어맞는지는 axiom이 아니라 실측 필요 — 오늘 세션의 LTX 소켓연결 실패들(노드이동 오인식 등)도 이 분류로 커버되는지 사후검증 가치 있음.
