# 0008. 메뉴 전용 초경량 비전모델 (아이디어 메모, git 미반영)

- Status: Idea memo (2026-08-25) — **의도적으로 git에 커밋하지 않음**(user 지시, u_2269). 로컬 참고용.
- Deciders: user 제안(u_2268/2269), 오케 정리

## Context

지금 kong-bot 워커는 a11y 트리 기반으로 대부분의 UI 조작(메뉴 클릭, 버튼 탐색 등)을 처리하고 있음. 문제가 되는 건 a11y가 안 먹히는 영역(WebGL 캔버스 등, 오늘 ComfyUI 소켓연결 사례)뿐. 그런데 a11y 자체가 아예 없거나 부실한 앱(레거시 앱, 일부 게임, 특수 렌더링 앱)을 다뤄야 할 상황도 있을 수 있어, "메뉴 구조를 비전으로 인식하는 경량모델"을 별도로 학습시키자는 아이디어.

## Idea (user 2026-08-25)

OS 앱들의 표준 메뉴(파일·보기·편집·도움말 등)는 상세 항목은 앱마다 다르지만 **구조 패턴(위치·드롭다운 형태·계층)은 공통점이 많음**. 이 공통 패턴만 특화 학습하면 범용 비전모델보다 훨씬 가볍고 정확한 "메뉴 전용 인식기"를 만들 수 있지 않을까.

**구체 학습전략 제안(u_2269)**: 메뉴 하나(예: "파일" 메뉴)만 떼어서 **해상도별로 각각 학습**하면(1920x1080, 2560x1440, 3456x2234 Retina 등 주요 해상도마다 별도 샘플) 10회 이상의 반복 학습으로도 실용적인 인식률을 확보할 수 있지 않을까 — 즉 범위를 "모든 메뉴 전체"가 아니라 "메뉴 하나 × 해상도 여러 개"로 좁혀서 학습 난이도 자체를 낮추자는 전략.

## 오케 평가

- **범위 좁히기 전략 자체는 타당함.** "파일 메뉴"라는 단일 카테고리는 대부분 앱에서 열기/저장/다른이름으로저장/최근항목/인쇄/종료 같은 몇 가지 표준 항목의 조합이라, 변이(variation)가 크지 않음 — 적은 샘플로도 수렴 가능성 높음.
- **해상도별 분리 학습**은 절충이 필요: 해상도가 다르면 절대좌표는 달라지지만 상대적 레이아웃 비율(메뉴바 높이 대비 위치 등)은 보존되는 경우가 많음 — 해상도별로 완전히 별도 모델을 만들기보다, 좌표를 정규화(0~1 비율)해서 하나의 모델이 해상도 무관하게 일반화하도록 학습하는 편이 데이터효율이 더 좋을 수 있음. 다만 이건 검증 전 가설.
- **a11y와의 역할분담**: 이미 a11y가 있는 앱(대부분의 macOS 네이티브·표준 웹앱)은 굳이 비전모델이 필요 없음 — 이 경량모델은 **a11y가 없거나 부실한 앱** 전용으로 스코프를 명확히 좁히는 게 투자 대비 효율적. 오늘 겪은 문제(ComfyUI WebGL 캔버스)는 "메뉴"가 아니라 "그래프 에디터 캔버스 요소" 인식이 필요한 다른 문제라, 이 아이디어와는 별도 트랙으로 봐야 함.

## Open Questions

1. 학습 데이터를 어떻게 모을 것인가 — 스크린샷 직접 촬영+수동 라벨링(메뉴항목 bbox)인지, 기존 UI 데이터셋(RICO, Screen2Words 등) 활용 가능한지 리서치 필요.
2. "10회 이상 학습"이 의미하는 게 epoch 수인지 샘플 수인지 명확화 필요 — 소규모 파인튜닝(few-shot)이라면 10개 샘플로도 유의미할 수 있으나, 처음부터 학습(from scratch)이라면 훨씬 많은 데이터 필요.
3. 이 경량모델을 kongtrol 파이프라인에 어떻게 끼워넣을지(a11y 우선 시도 → 실패시 이 모델로 폴백, 이라는 구조가 될 듯) — [[breakthrough-a11y-uitars]] 메모리의 "a11y tree+UI-TARS 하이브리드" 방향과 같은 결이라 참고할 것.
4. 캔버스/WebGL 전용 별도 모델(오늘 문제 해결용)과는 완전히 다른 트랙 — 혼동하지 말고 별도 프로젝트로 취급.
