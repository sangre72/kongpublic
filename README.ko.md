# kong-bot

*[English](./README.md) | 한국어*

> 사람처럼 화면을 보고 판단해서, 사람처럼 마우스/키보드로 조작하는 AI 에이전트 시스템.
> 텔레그램으로 지시를 받아 GUI 앱(Krita, Keynote, 브라우저 등)을 실제로 조작해 작업을 완수합니다.

## 시작한 이유

MCP, 스킬, API — 다 좋은 도구들입니다. 그런데 결국 회사가 커지고 사용자가 늘어나면, 대부분은 어떤 형태로든 유료화됩니다. 사업적으로는 당연한 흐름이지만, 그 말은 곧 새로운 앱을 하나 연결할 때마다 새로운 구독료, 새로운 API 키, 새로운 청구서가 따라온다는 뜻이기도 합니다.

이 프로젝트는 조금 다른 전제에서 출발했습니다 — 저는 이미 데스크탑을 갖고 있고, 이미 구매했거나 무료로 쓸 수 있는 실제 앱들(그림도구, 프레젠테이션도구, 브라우저 등)을 갖고 있습니다. 앱마다 AI 전용 유료버전을 새로 사는 대신, AI가 제가 이미 가진 앱들을 — 제가 하듯이 화면을 보고 마우스·키보드로 — 그냥 그대로 쓰게 하면 되지 않을까 하는 생각이었습니다.

kong-bot은 그걸 가능하게 하려는 프로젝트입니다 — 이미 가지고 있거나 무료로 쓸 수 있는 모든 앱을, 새로운 유료 연동 없이 AI가 자유롭게 함께 쓸 수 있도록.

## 프로젝트 개요

kong-bot은 **오케스트레이터(orch)**와 **워커(worker)** 두 개의 Claude 세션이 협업하는 구조로 동작합니다.

- **사용자**는 텔레그램으로 자연어 지시를 보냅니다.
- **오케스트레이터**는 지시를 받아 실행 가능한 작업 지시서(`a_*`)로 변환해 워커에게 전달하고, 결과(`ar_*`)를 검증한 뒤 텔레그램으로 보고합니다.
- **워커**는 실제 화면을 보고(`kongtrol see`), 판단하고, 마우스/키보드로 조작해서(`kongtrol input`) 작업을 수행합니다.

핵심 원칙은 **"스크립트로 결과물을 생성하지 않는다"**는 것입니다. 슬라이드를 만들든 그림을 그리든, 산출물은 반드시 실제 앱을 사람처럼 조작해서 만들어냅니다. 앱마다 하드코딩된 제어 로직도 두지 않습니다 — 하나의 범용 코어가 화면을 보고 판단하며, 앱별 지식은 재사용 가능한 레시피(`kaymaps/`)로 데이터화되어 쌓입니다.

## 목적

1. **사람과 동일한 방식의 GUI 자동화**: 좌표를 미리 정해두는 매크로가 아니라, [관찰 → 판단 → 물리적 입력]을 반복하는 실시간 루프.
2. **범용 에이전트 코어**: 특정 앱 전용 코드를 만들지 않고, 하나의 코어가 어떤 GUI 앱이든 다룰 수 있도록.
3. **학습의 축적**: 한 번 검증된 조작법(클릭 좌표, 메뉴 경로, 색상 선택 공식 등)은 레시피로 저장해 다음에는 시행착오 없이 재사용.
4. **원격 협업**: 텔레그램을 통해 어디서든 지시하고 진행 상황을 실시간으로 확인.

## 최근 중점 작업 (2026-09)

이번 작업은 **속도·확장성·경험 축적**에 집중했습니다.

- **기호 통신 프로토콜 (COMM#0)**: 오케↔워커 사이 요청·응답을 산문이 아니라 압축된 수식·기호로 주고받습니다. 한글은 유저에게 보내는 텔레그램 답변에만 사용 — 매 왕복의 토큰·지연을 줄입니다.
- **payload-in-wake**: 지시/결과를 wake 주입에 통째로 실어, 워커가 파일을 열지 않고 즉시 실행합니다. `a_/ar_` 파일은 다음 세션 재시작용 흔적으로 유지.
- **잡 레지스트리** (`kaymaps/_jobs_registry.json`): 반복 작업을 데이터로(키워드→레시피·경로공식·실행순서/의존·모델). 레지스트리에 있는 요청은 고민 없이 즉시 배정 — 계약서는 얇게 두고 규약은 데이터로 늘립니다.
- **GOAL-ONLY-THINK + 성능 튜닝**: 워커는 목적에 필요한 것만 생각(알려진 스텝 재고민 금지). 네비게이션은 a11y 조회 + 즉시 클릭(하드코딩 좌표 금지 — 창/줌에 따라 좌표가 변하므로 실시간 조회 필수). 실측: 스텝당 ~15초 → ~2초, 병목은 페이지 렌더.
- **즉시 정지** (`orch_stop_worker.sh`): ESC 하드 인터럽트로 진행 중인 워커 턴을 그 자리에서 끊습니다(일반 wake는 턴 뒤로 밀림).
- **경험 뱅크** (별도 레포 `kong-agent-experience-bank-`): 분야별(구매/항공권/…) 지식을 검증된 `EXP_*` 엔트리로 `<국가>/<언어>/<사이트>/<도메인>/` 구조에 축적. 분야 작업 시 먼저 참고하고(예: 최저가 = 표시가 아닌 실결제액) 끝나면 기록.
- **성격별 검증 (verify-by-failure-mode)**: CLI/exit-code 작업은 exit 코드만 신뢰(재확인 없음), GUI 작업(무성실패 가능)은 정확히 1회만 검증.
- **아이콘 인식 모델 (리서치)** (`research/src/icon_learning/`): 범용 UI 아이콘 100종(add/delete/edit/close/…)을 분류하는 ResNet18 CNN. 테스트 정확도 ~90.6%, 추론 ~1.4ms. 텍스트·a11y 라벨이 없는 아이콘 전용 컨트롤의 빠른 폴백 용도. 현재는 리서치 단계 — 학습·평가는 됐지만 실사용 루프엔 아직 미연결(기본 컨트롤 탐색은 a11y 조회 유지, 범용적이고 아이콘별 모델이 불필요하므로).

## 구성도

```
                          사용자 (텔레그램)
                                │
                                ▼
                    ┌───────────────────────┐
                    │   Orchestrator(orch)    │
                    │  - 지시 정제(u_ → a_)    │
                    │  - 결과 검증(ar_)         │
                    │  - 텔레그램 보고/질의       │
                    └───────────┬───────────┘
                                │ protocol/{a,ar}
                                ▼
                    ┌───────────────────────┐
                    │      Worker            │
                    │  ┌─────────────────┐  │
                    │  │  BRAIN (판단)     │  │
                    │  │  "무엇을 할지"     │  │
                    │  └────────▲────────┘  │
                    │           │ 화면정보/결정 │
                    │  ┌────────┴────────┐  │
                    │  │ EYES  │  HANDS  │  │
                    │  │(관찰) │ (조작)   │  │
                    │  └───────┴─────────┘  │
                    └───────────┬───────────┘
                                │ kongtrol CLI
                                ▼
                    ┌───────────────────────┐
                    │   대상 GUI 앱            │
                    │  (Krita, Keynote, ...)  │
                    └───────────────────────┘
```

### 계층별 역할

| 계층 | 구현 | 역할 |
|------|------|------|
| **Eyes (관찰)** | `kongtrol see --a11y`, 스크린샷 | 화면의 UI 요소(역할·라벨·좌표)를 논리 좌표로 추출, 픽셀 단위 시각 정보 확보 |
| **Hands (조작)** | `kongtrol input` (click/move/drag/text/key) | 실제 마우스·키보드 이벤트 주입(CGEvent 기반, 사람 속도 시뮬레이션 지원) |
| **Brain (판단)** | Claude(워커 세션) | 화면 상태를 보고 다음 행동을 결정. 좌표는 계산하되, "무엇을 클릭할지"는 시각적으로 판단 |
| **Protocol (통신)** | `telegram_bot/orchestrator/protocol/{u,a,ar}` | orch↔worker 간 지시서·결과 파일 교환 |
| **Recipe (기억)** | `kaymaps/<app>/RECIPE_*.txt` | 앱별로 검증된 조작법(정확한 좌표, 메뉴 경로, 공식 등)을 재사용 가능하게 저장 |

### 화면 배율

클릭 좌표는 항상 **a11y 논리좌표 + `kongtrol input click --scale 1.0`**을 사용한다 — 스크린샷의 픽셀 좌표를 그대로 쓰지 않는다.

- 이 개발 환경의 실제 디스플레이 배율은 **2배(Retina)**다. 스크린샷의 픽셀 크기(예: 4112x2658)는 클릭 레이어가 기대하는 논리 좌표계와 다르므로, 픽셀 좌표를 클릭에 쓰려면 반드시 배율로 나눠 환산해야 한다.
- 이미지에서 좌표를 반환하는 외부 모델(로컬 VL 서버, OmniParser 등)은 **스크린샷 픽셀 기준** 좌표를 준다. 이를 그대로 클릭에 넣으면 안 되고, 반드시 논리좌표로 환산한 뒤 사용한다.
- 애매하면 스크린샷에서 좌표를 역산하기보다 `kongtrol see --a11y` 출력(이미 논리좌표)을 우선 사용한다.

### VLM binary 판단 활용 (`kongtrol see --vl`)

`kongtrol see --vl "<프롬프트>"`는 스크린샷을 캡처해 640px로 리사이즈한 뒤 로컬 VL 서버(Qwen3-VL-8B)로 보내 텍스트 판단을 받는다. CapCut·Google Flow 등 캔버스 렌더링 UI에서 `--a11y`가 라벨 있는 요소를 거의 못 잡을 때의 보완 수단이며, a11y가 되는 곳에서는 항상 a11y가 1순위다.

**사용 기준(실측, ar_942/ar_943):**

| 판단 유형 | 정확도 | 평균 소요시간 | 결론 |
|---|---|---|---|
| 단순 유무("X가 열려있나/보이나?") | 5개 중 4개 정답 | ~0.45초 | ✅ 사용 가능 |
| 소수 개수(1~2개) | 5개 중 4개 정답 | ~0.45초 | ✅ 사용 가능 |
| 화면 종류 판별 | 양호 | ~2~5초 | ✅ 사용 가능 |
| 정확한 개수(3개 이상) | 5개 중 0개 정답 | ~2~5초 | ❌ 사용 금지 |
| 텍스트 원문 인용 | 5개 중 0개 정답 | ~2~5초 | ❌ 사용 금지, 환각 발생 |
| 메뉴/목록 전체 나열 | 5개 중 0개 정답 | ~2~5초 | ❌ 사용 금지, 환각 발생 |

"사용 금지" 쪽의 실패 양상은 단순 오답이 아니다 — 실제로 없는 UI를 그럴듯하게 지어낸다(존재하지 않는 메뉴 항목을 만들어내거나, 화면에 없던 텍스트를 인용하는 식). 이 범주의 판단은 별도 검증 없이 그 결과로 행동하면 안 된다.

**예시**: `kongtrol see --vl "클립 경계에 트랜지션 아이콘이 있는가? 예/아니오"` — 적합. `kongtrol see --vl "좌측 사이드바의 모든 항목을 나열해줘"` — 부적합, `--a11y`를 쓰거나 스크린샷을 직접 확인할 것.

## 부족한 부분

- **VLM 세밀판단 신뢰불가**: 로컬 VL모델(`kongtrol see --vl`)은 있다/없다 이진판단·소수(1~2개) 카운트에서만 신뢰할 수 있습니다(측정치는 아래 영문판 표 참고). 정확한 개수·텍스트 인용·전체목록 나열은 그럴듯하지만 틀린 답을 지어내는 경향(실측 0/5 정답)이 있어, 이런 경우엔 `--a11y` 또는 화면을 확대 크롭해 직접 읽는 방식이 필요합니다.
- **GUI-grounding 벤치마크모델 도입 보류**: 클릭·grounding 전용 특화모델(UI-TARS류) 도입을 초기에 검토했으나 통합은 보류된 상태입니다. 현재 파이프라인은 `--a11y` 논리좌표를 1순위로, VLM은 이진판단 보조수단으로만 사용하며 전면적인 grounding 대체는 하지 않습니다.
- **일부 개발서버의 원인불명 간헐적 hang**: 초기 데모에 사용된 로컬 `uvicorn --reload` 개발서버 하나가 20~80초씩 간헐적으로 응답불가 상태에 빠지는 현상이 있었으나, 그 서버 소스 자체가 이 저장소 밖에 있어 블랙박스 read-only 진단만 가능했고 근본원인은 미확인 상태입니다. 현재는 대기 후 재시도로 우회하고 있으며, 코드레벨 수정은 해당 서버 소스 접근이 필요합니다.
- **좌표·입력 레시피는 경험적 축적, 전수조사 아님**: `kaymaps/`는 에이전트가 실제로 마주치고 검증한 앱·UI요소만 커버합니다. 사전구축된 UI 카탈로그가 아니라 실사용을 통해 레시피 단위로 점진 확장됩니다.

## 앞으로 할 부분

- 더 많은 앱·UI요소 유형으로 레시피 커버리지 확대(`kaymaps/`의 경험적 학습모델은 사전 투입보다 사용량에 비례해 확장).
- 오케스트레이터↔워커 프로토콜의 단일워커/단일fork 원칙 강화(동일 물리 마우스/키보드 대상에 중복·병렬 조작 방지).
- 장시간 세션 안정성 지속 강화(크래시·trust다이얼로그·세션생존감시 워치독은 이미 존재, 새로운 실패유형 발견시 커버리지 계속 확장).
- 캔버스 위주 앱에서 `--a11y`우선+VLM이진보조 방식이 커버리지 한계에 부딪히면 전용 GUI-grounding 모델 재검토.

## 디렉토리 구조

```
kongtrol/              Rust 기반 순수 IO 도구(화면인식 + 마우스/키보드 조작 CLI)
telegram_bot/           텔레그램 봇 + 오케스트레이터/워커 프로토콜
  orchestrator/
    protocol/{u,a,ar,archive,refs}  사용자 지시 · 작업지시서 · 결과보고 · 첨부이미지
    och.txt              오케 규칙(COMM#0, GATE, 원칙)
    worker_1.txt         워커 규칙(RULE#0 goal-only-think)
    scripts/             wake 주입(orch_wake_self/worker), orch_stop_worker(ESC), 감시
kaymaps/                 앱별 검증된 조작 레시피(재사용 가능한 학습결과)
  _common/               앱 무관 범용 원칙/교훈
  _jobs_registry.json    반복 작업을 데이터로(키워드→레시피/경로/실행)
  krita/, keynote/, localhost-cinebot/, chrome/, system/   앱별 레시피
jobs/                    작업 산출물(영상·이미지·편집물, 잡별 디렉토리)
docs/                    ADR, 앱 지식베이스, 리서치 문서
```

관련 레포: **`kong-agent-experience-bank-`** — 분야별(구매·항공권·…) 검증 경험을 공유가능한 `EXP_*` 엔트리로, `<국가>/<언어>/<사이트>/<도메인>/` 구조로 축적.
